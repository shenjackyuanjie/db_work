# 柑橘果园智能诊断与管理系统设计与实现

## 摘要

针对柑橘种植中病害识别依赖人工经验、环境监测与任务管理缺乏闭环等问题，本文设计并实现了一套集病害智能诊断、环境监测、任务管理与三维可视化于一体的综合管理系统。系统采用 Rust + Axum 构建后端服务，PostgreSQL 持久化存储，Tract ONNX 本地推理与 OpenRouter 远端 AI 混合引擎实现叶片病害二阶段识别与置信度校准；前端通过 Three.js 提供 3D 果园沙盘，前后端同端口部署。系统涵盖用户认证、病害识别、温湿度采样、任务管理、施肥建议生成及管理员后台等完整功能模块。

## 一、项目背景与意义

柑橘种植长期面临黄龙病、溃疡病、沙皮病等多种病害威胁，传统人工巡检效率低、难以覆盖大面积果园，且早期症状不易察觉。现有农业信息化工具往往将图像识别与环境监测割裂，病害诊断难以结合实时温湿度进行综合研判。果园日常管理中还存在任务派发无记录、施肥凭经验、园区状态不可视等问题。

本系统致力于构建"感知—诊断—决策—执行"闭环：感知层将叶片图像与温湿度数据融合，引入气候佐证机制提升病害判别准确度；决策层基于识别记录与环境态势自动生成农事任务，并通过大语言模型输出结构化施肥方案；展示层通过 Three.js 3D 沙盘直观呈现果园全局状态，管理员后台提供用户管控与审计能力。

## 二、需求分析

**普通用户需求**：注册登录登出，上传叶片图片进行病害识别，查看置信度、严重程度与治疗建议；浏览温湿度采样数据、健康点统计与任务列表；通过 3D 沙盘查看园区布局；基于识别历史或手动触发生成施肥建议。

**管理员需求**：除普通用户权限外，需管理用户列表、创建查询邀请码、审核待注册用户；查阅审计日志与仪表盘统计；按用户维度聚合果园总览数据；动态调整系统设置无需重启服务。

**系统需求**：PostgreSQL 持久化，启动自动建表与演示数据初始化；推理层支持本地 ONNX（纯离线）与混合模式（本地过滤+远端分析）灵活切换；单一端口承载静态资源、HTTP API 与图片归档；所有诊断、采样、任务、审计操作均落库可追溯。

## 三、系统总体设计

系统采用三层 B/S 架构。**表现层**由 `static/` 中的 HTML/CSS/JS 页面构成：`index.html`（公开首页）、`analyze.html`（识别页，需登录）、`admin.html`（管理后台，需管理员权限）、`orchard-3d.html`（Three.js 3D 沙盘）。表现层通过 HTTP API 与服务层通信。

**服务层**基于 Rust + Axum 构建。`server.rs` 中 `create_router()` 注册所有路由，`AppState` 共享 OpenRouterClient、InferenceRuntime 和 PgPool。`handlers_core/` 处理看板、温湿度、任务及记录接口；`handlers_ai/` 负责病害识别、AI 分析和施肥建议；`user_routes/` 实现认证、会话与管理后台；`inference/` 封装 ONNX 和远端混合推理。中间件层包含请求日志与 CORS 支持。

**数据层**使用 PostgreSQL，通过 SQLx 异步访问（最大连接 3），共 11 张核心表，启动时自动建表。

```
浏览器前端 (HTML/CSS/JS + Three.js)
  |
  v
Axum 后端 (Rust + Tokio)
  |-- 用户与会话模块
  |-- 病害识别模块
  |-- 温湿度与任务模块
  |-- 管理员后台模块
  |-- 果园沙盘数据模块
  |
  |-- PostgreSQL    |-- ONNX (Tract)    |-- OpenRouter (Reqwest)
```

## 四、技术选型

- **Rust 2024**：系统语言，内存安全与零成本抽象，适合稳定性要求高的后端场景
- **Tokio + Axum**：异步运行时与 Web 框架，路由和状态管理具编译期检查
- **SQLx + PostgreSQL**：编译时 SQL 校验，PgPool 管理连接池
- **Tract ONNX**：纯 Rust 的 ONNX 推理引擎，无 C 依赖，编译部署简便
- **Reqwest**：HTTP 客户端，调用 OpenRouter 等外部 AI 服务
- **Serde**：统一 JSON 与 TOML 序列化反序列化
- **Tower HTTP**：CORS 中间件与静态文件托管
- **Three.js**：前端 3D 渲染（CDN 加载）
- 辅助：image (图片预处理 224×224 归一化)、base64、tracing、chrono、anyhow

## 五、功能模块设计

### 5.1 用户认证

支持开放注册与邀请码注册双模式。普通注册写入 `app_pending_users` 待管理员审批；邀请码注册校验 `app_invitations` 后可跳过审批。登录生成 Token 存入 `app_sessions`，后续请求通过 Cookie/Header 校验。密码哈希存储，is_admin 字段区分角色。关键数据表：`app_users`、`app_sessions`、`app_invitations`、`app_pending_users`。

### 5.2 病害识别

支持图片上传（multipart/form-data）与 Base64 编码两种输入方式，可选附带温湿度及区域参数，通过基础版（`/api/citrus-disease`）和增强版（`/api/citrus-disease-v2`）两个接口提供服务。识别采用两阶段级联推理架构：第一阶段由 Model 1（果树识别模型）判断输入图像是否为柑橘叶片，若非果树则直接返回结果并提示重新拍摄；第二阶段由 Model 2（病害分类模型）在黄龙病、溃疡病、沙皮病、健康四类中输出分类标签及置信度。增强版在此基础上引入温湿度校验机制：为每种病害定义 ClimateProfile（包含温度与湿度的适宜区间和峰值区间），采用梯形隶属度函数量化当前温湿度对各病害的环境佐证强度，据此对图像分类概率进行加权修正，使环境因子与视觉特征协同决策，降低单一模态的误判风险。每次识别结果完整写入 `app_diagnosis_records` 表，上传图片经 Base64 解码后以 JPG 格式归档至 `static/uploads/` 目录，通过 `/media/recognition_records/*` 路径提供静态访问。

### 5.3 推理与 AI

本地推理基于 Tract ONNX，图片经 Base64 解码→RGB→Resize 224×224→归一化（mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]）→送入模型，Softmax 后取最大置信度类别。处置建议内置映射：黄龙病（控木虱+清病株）、溃疡病（药-剪-药）、沙皮病（清园+药剂）。远端推理通过 Reqwest 调用 OpenRouter Chat API，支持结构化 JSON 输出与供应商偏好配置。施肥建议模块接收土壤参数，调用 LLM 生成包含肥料推荐和施用计划的结构化方案。

### 5.4 环境监测与任务管理

温湿度支持普通采样和带标签序列号的树传感器采样，通过 `tag_serial_number` 关联树位。环境风险分三级：22-32°C + 80-100% 湿度为高风险，15-35°C + 60-80% 为中风险。任务支持 CRUD 及自动生成——根据病害名称或环境风险等级自动创建对应治理任务，包含风险等级、类型、来源与完成状态。

### 5.5 管理员与沙盘

管理员接口挂载 `/user/admin/*`，涵盖用户管理、邀请码创建查询、待审核审批、系统设置读写（注册开关、维护模式、置信度阈值等）、仪表盘统计及审计日志。`orchard-3d.html` 基于 Three.js 渲染 3D 沙盘，数据来自 `app_orchard_trees`（20 棵演示树，坐标 0-500，地形 9.7-13.8m）、`app_tree_sensor_records`（每树 3 条采样）和 `app_diagnosis_records`。首次启动自动初始化演示数据。

## 六、数据库设计

11 张表通过 `bootstrap.rs` 启动时 `CREATE TABLE IF NOT EXISTS` 自动创建：

| 分类 | 表名 | 用途 |
|------|------|------|
| 用户权限 | `app_users` | 账号、密码哈希、管理员标记、坐标 |
| | `app_sessions` | 登录 Token |
| | `app_invitations` | 邀请码及有效期 |
| | `app_pending_users` | 待审核注册 |
| 业务 | `app_diagnosis_records` | 识别结果、置信度、处置建议、图片路径 |
| | `app_tasks` | 治理任务、风险等级、完成状态 |
| 环境 | `app_temperature_humidity` | 温湿度采样 |
| 果园 | `app_orchard_trees` | 树位编码、坐标、地形高度 |
| | `app_tree_sensor_records` | 树传感器采样 |
| 管理 | `app_system_settings` | 全局配置单行存储 |
| | `app_admin_audit_logs` | 管理员操作审计 |

密码不存明文，关键字段建索引。生产环境建议引入独立迁移工具。

## 七、接口设计

统一响应格式 `{code, message, data, timestamp}`，按功能分组：

- **基础会话**：`GET /health`、`POST /api/register`、`POST /api/login`、`POST /api/logout`、`POST /api/validate`、`POST /user/me`
- **病害识别**：`POST /api/citrus-disease`（基础版）、`POST /api/citrus-disease-v2`（增强版）、`POST /citrus/analyze`（OpenRouter 分析）、`GET /api/recognition-records`、`GET /api/disease-treatment`、`GET /media/recognition_records/*`
- **环境与任务**：`GET/POST /api/temperature-humidity`、`GET /api/tasks`、`POST /api/tasks/add`、`POST /api/tasks/complete`、`POST /api/tasks/generate/disease`、`POST /api/tasks/generate/environment`、`GET /api/health-point`、`POST /user/orchard/overview`
- **施肥建议**：`GET /api/generate`、`POST /api/generate/fertilization-plan`
- **管理员**：`/user/admin/*`（用户管理、邀请码、审批、设置、仪表盘、审计日志）

受保护接口校验 Token，管理员接口额外校验 `is_admin`。未登录访问 `analyze.html` 或普通用户访问 `admin.html` 均被重定向。

## 八、部署与运行

**前提条件**：Rust 1.85+、PostgreSQL 实例、ONNX 模型文件、OpenRouter API Key、可访问 jsDelivr CDN。

**配置脱敏示例**：

```toml
[server]
addr = "0.0.0.0:11000"
log_level = "info"

[ai]
openrouter_api_key = "sk-or-v1-your-key"

[database]
postgres_url = "postgres://user:password@127.0.0.1:5432/db_name"

[inference]
mode = "onnx"
model_1_path = "onnx/model_1.onnx"
model_2_path = "onnx/model_2.onnx"
```

**启动流程**：准备数据库→放置模型文件→修改 config.toml→`cargo run --release`→自动建表与演示数据初始化→访问 `http://127.0.0.1:11000/index.html`。服务监听 Ctrl+C/SIGTERM 实现优雅关闭。

## 九、测试计划

系统测试覆盖功能、接口、数据、安全四个维度。**功能测试**验证全部核心业务流程：注册（开放注册、邀请码注册、重复用户名拒绝、管理员审批通过与驳回）、登录登出（正确凭证返回 Token、错误密码拒绝、登出后 Token 即时失效）、病害识别（上传真实柑橘病害叶片图片验证返回字段完整性——预测类别、置信度、病害名称、严重程度、治疗建议和预防措施；上传非叶片图片验证正确返回"非果树"结果）、识别记录分页查询、温湿度采样提交与回读一致性、任务手动新增/标记完成/根据病害名称自动生成/根据温湿度自动生成、管理员各项功能（用户列表、邀请码创建查询、待审核审批、系统设置修改、仪表盘统计、审计日志查看）、以及四个前端页面正常加载。

**接口测试**使用 curl 工具验证正常与异常场景：正常参数加有效 Token 应返回 `code:200` 及正确数据；异常场景包括必填参数缺失、无效或过期 Token 访问受保护接口、普通用户 Token 越权访问 `/user/admin/*` 路径、请求不存在的资源等，均需验证返回恰当的错误码和消息，且统一响应格式 `{code, message, data, timestamp}` 在所有场景下保持一致。

**数据测试**验证服务首次启动行为：11 张表全部自动创建；`app_system_settings` 写入正确默认值；果树表与传感器表为空时自动初始化 20 棵演示树和每树 3 条采样记录；识别记录入库后各字段值与原始请求参数严格一致；识别图片正确归档并可公开访问；任务新增和完成操作后数据库状态即时更新。

**安全测试**验证权限边界：未登录访问 `/analyze.html` 和普通用户访问 `/admin.html` 均被重定向至首页；无效 Token 调用 `/api/validate` 返回认证失败；普通用户 Token 调用管理员接口返回权限不足；确认数据库中密码字段为哈希值而非明文；检查版本控制中不包含 config.toml 真实配置。

## 十、安全性与可维护性

**已实现措施**：基于 Token 的登录态校验（登录生成 Token 存入 `app_sessions`，后续请求通过 Cookie 或 Header 携带验证）；管理员权限隔离（`is_admin` 字段区分角色，管理员接口通过中间件校验，普通用户访问受限）；用户密码经哈希处理后存储，数据库中不保留明文；系统支持维护模式（`maintenance_mode`）和注册开关（`open_registration`），管理员可动态调整无需重启；所有管理员关键操作（用户审批、权限变更、设置修改等）均写入 `app_admin_audit_logs` 审计日志，记录操作类型、操作者和时间戳；每次病害识别完整保留参数、结果和用户信息，支持事后追溯；数据库连接串和 API Key 等敏感配置集中存放于 `config.toml`，代码中不硬编码。

**当前不足**：数据库采用启动时 `CREATE IF NOT EXISTS` 方式建表，缺少正式的版本化迁移管理，生产环境建议引入 refinery 或 sqlx-cli migrate 工具；自动化测试目前集中在 ONNX 推理逻辑的单元测试，缺少 HTTP 接口的集成测试和端到端回归测试；前端 HTML/JS 页面与后端 Rust 服务耦合在同一进程内，若需独立部署前端或使用 CDN 分发静态资源则需拆分架构；3D 沙盘依赖 jsDelivr CDN 加载 Three.js，在离线或 CDN 不可达的环境下无法正常渲染，建议本地化前端依赖；当前会话 Token 无自动过期清理机制，长期运行可能积累大量过期会话；密码哈希算法可进一步升级至 bcrypt 或 argon2 等抗暴力破解方案；仅提供 HTTP 明文服务，生产环境建议配置 TLS 证书或前置 Nginx 反向代理做 HTTPS 终结。

## 十一、总结与展望

系统已完成从病害智能识别到农事任务闭环管理的全链路功能建设。病害识别模块实现两阶段级联推理——先甄别果树叶片再细粒度四分类，并创新性地引入温湿度气候佐证机制对分类结果进行环境校验；环境监测模块支持普通采样与树传感器绑定采样双模式，依据温湿度自动划分环境风险等级；任务管理模块支持手动增删查改及基于病害和环境风险的自动治理任务生成；施肥建议模块通过大语言模型输出包含肥料配比和施用计划的完整农事方案；管理员后台提供用户管控、邀请码审核、系统设置与审计追溯等企业级功能；3D 果园沙盘基于 Three.js 实现果树位置、地形高度和健康状态的三维可视化呈现。系统后端采用 Rust + Axum 架构，在编译期确保内存安全与类型安全；推理层同时支持纯本地 ONNX（Tract 引擎，零 C 依赖）和远端 OpenRouter AI 分析两种模式，可根据实际部署环境的网络条件和延迟要求灵活切换；所有服务在单一端口上承载，启动时自动完成建表和演示数据初始化，降低部署运维复杂度。

后续优化方向涵盖八个方面：引入数据库迁移工具（如 refinery）实现版本化 DDL 管理与回滚；建立 API 集成测试和 CI/CD 流水线提升交付质量；从当前四类病害扩展至炭疽病、煤烟病等更多柑橘病害乃至跨作物支持；对接真实田间物联网传感器（温湿度、土壤墒情、光照等）替代模拟数据；增加短信、邮件或站内消息等主动告警通道；优化 3D 沙盘的离线加载方案和大规模树位场景下的渲染性能；升级密码哈希至 bcrypt/argon2、引入会话过期自动清理并支持 HTTPS 部署；基于累积的历史识别记录与环境数据，构建病害趋势分析和防治效果评估报表，为果园管理提供数据驱动的决策支持。
